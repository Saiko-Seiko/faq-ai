# デモから本番システムへ — 段階計画

## いまの状態と、本番との距離

デモは「動いて見える」ところまで到達している。
ただし、本番として運用するには決定的に足りないものが3つある。

| 足りないもの | 何が起きるか |
|---|---|
| **記録が残らない** | 面接の記録が閲覧者のブラウザにしか無い。人事Aが見た結果を人事Bは見られない。端末を変えたら消える |
| **誰でも見られる** | 応募者の回答（＝個人情報）に、URLを知っていれば誰でも到達できる |
| **URLが使い回せる** | `?token=demo-tanaka` は推測でき、期限も無く、何度でも受験できる |

この3つは**採用業務では致命的**なので、本番化の順序はここから決まる。

---

## 段階

順序は「守るべきものが多い順」で決めている。
データが残らないうちに認証を作っても意味がなく、
個人情報を保存し始めたら、その瞬間から保護の責任が発生する。

### Stage 1 — 記録の永続化（データ基盤） ✅ 実装済み

面接の記録をサーバーのデータベースに保存し、人事が共有して見られるようにする。
同時に、応募者データの読み取りに鍵を掛ける。

- データベース設計（候補者・面接記録・操作ログ）
- 保存と取得のAPI
- 応募者データの読み取りを、鍵を持つ人だけに限定する
- データベース未設定なら、これまで通りデモとして動く（後方互換）

**完了条件:** 別々の端末・別々のブラウザから同じ面接記録が見え、人事の判断が共有される。

### Stage 2 — 候補者URLの発行 ✅ 実装済み

推測できない一意のURLを発行し、期限と使用回数を管理する。

- 署名付きトークンの発行（推測不可・期限あり・原則1回きり）
- 人事画面から候補者を登録し、URLを発行する導線
- 受験状況の管理（未受験／受験中／完了／期限切れ）
- 案内メールの送信（差し込み文面）

**完了条件:** 人事が候補者を登録するとURLが発行され、期限切れ後は開けない。

### Stage 3 — 人事のログインと操作ログ ✅ 実装済み

Stage 1 の暫定的な鍵を、本来の認証に置き換える。

- 人事担当者のログイン（メールリンク認証を想定。パスワード管理を持たない方式）
- 担当者ごとの権限（閲覧のみ／判断可）
- 操作ログ（誰がいつ誰を合格にしたか）
- Stage 1 の共有トークンを廃止

**完了条件:** 「なぜこの人を不合格にしたのか」に、記録で答えられる。

### Stage 4 — 個人情報の運用 ✅ 実装済み

法令と社内規程に沿った状態にする。**Stage 5 より先**に行う。

- 保存期間と自動削除（例：不採用者は6ヶ月で削除）
- 応募者からの削除請求への対応手段
- 同意取得の文面を、クライアントの個人情報保護方針と突き合わせる
- 保存データの暗号化とアクセス範囲の確定

**完了条件:** 「応募者のデータはどこに何ヶ月あり、誰が見られるか」に即答できる。

### Stage 5 — 運用をクライアントに引き渡す

開発者を介さずに、人事が自分で運用できるようにする。

- ナレッジの編集画面（制度変更のたびに依頼が来る状態をなくす）
- 面接の質問と評価基準の編集画面
- 実際の会社情報への差し替え（架空データの撤去）
- 説明会動画の差し替えと配信

**完了条件:** 福利厚生が変わったとき、人事が自分で直せる。

### Stage 6 — 精度と運用改善

実際に使い始めてからでないと決められないもの。

- AIのスコアと、人事の最終判断のズレを集計する
- ズレの大きい評価軸のプロンプトを調整する
- よく聞かれてナレッジに無い質問を抽出し、追加候補として提示する

**完了条件:** 運用するほど精度が上がる仕組みがある。

---

## 順序について、あえて言っておくこと

**Stage 4（個人情報）を後回しにしない。**
Stage 1 で本物の応募者データを保存し始めた時点で、保護の責任は発生する。
Stage 2・3 と並行して、遅くとも実運用の開始前には終えておく必要がある。

**Stage 5 を軽く見ない。**
ここを飛ばすと「制度が変わるたびに開発者へ依頼」という状態が固定され、
クライアントにとっての運用コストになり、こちらにとっても細かい作業が続く。
双方のためにやったほうがよい。

## Stage 1 実装メモ

### 入れたもの

| ファイル | 役割 |
|---|---|
| `db/001_init.sql` | スキーマ（候補者・面接記録・操作ログ） |
| `api/_store.js` | データベースへの読み書き。未設定なら「保存先なし」を返す |
| `api/sessions.js` | 記録の保存（応募者・鍵不要）／一覧と合否（人事・鍵必要） |
| `assets/js/app.js` | `Sessions` が保存先を自動で切り替える |
| `assets/js/dashboard.js` | サーバーから読み、合否をサーバーへ書く |

### 決めたこと

**読み書きで必要な権限を分けた。**
応募者は自分の回答を送信できるが、他人の回答は読めない。
一覧の取得と合否の記録にだけ鍵を要求している。

**応募者からの送信で合否は上書きされない。**
`saveSession` は `human_decision` と `human_memo` に触らない。
面接記録の再送信で人事の判断が消えることがあってはならないため。

**保存はローカルが先、サーバーが後。**
通信に失敗しても応募者の回答は端末に残る。面接をやり直させない。

**データベースがあるのに鍵が無い場合は、データを出さずに 503 を返す。**
設定漏れが「誰でも読める状態」に繋がらないようにしている。

**本番では見本データを混ぜない。**
デモでは見本3件を常に表示するが、`DATABASE_URL` がある場合は
サーバーの記録だけを表示する。架空の候補者が本番の一覧に紛れ込まないように。

### 積み残し（意図的）

- **鍵は全員共通** … 操作ログの `actor` は `'hr'` 固定。Stage 3 で担当者ごとに
- **候補者はコード内に定義** … `CANDIDATES` のまま。Stage 2 でデータベースへ
- **削除の仕組みが無い** … Stage 4。保存を始めた以上、次に着手すべきはここ

### この環境で確認できたこと・できなかったこと

- ✅ デモ（localStorage）の動作は変わっていない — 自己診断 55項目すべてOK
- ✅ サーバー側ファイルの構文
- ❌ **データベースを繋いだ状態の動作** — この作業環境に Node と Postgres が無く、
  実行できていない。最初のデプロイ後、上記「動作の確認」を必ず実施すること

## Stage 2 実装メモ

### 入れたもの

| ファイル | 役割 |
|---|---|
| `db/002_candidates.sql` | 受験状況の列を追加（開始・無効化・案内送信） |
| `api/candidates.js` | 応募者の照会／人事の登録・無効化・期限延長 |
| `candidates.html` + `assets/js/candidates.js` | 候補者管理画面（人事用） |
| `assets/js/interview.js` | トークンをサーバーで検証し、期限切れ・受験済みを判定 |

### 計画から変えた点：署名付きトークン → ランダム＋DB管理

当初は署名付きトークン（JWTのような形）を想定していたが、**やめた。**

署名付きトークンは、発行後に**取り消せない**。
「間違った人に送ってしまった」「選考を取りやめた」というときに無効化できないのは、
採用業務では通用しない。同じ理由で「1回きり」も署名だけでは判定できない
（結局どこかに使用済みの記録が必要になる）。

Stage 1 でデータベースを入れた以上、ランダムな文字列をDBで管理するほうが
単純で、取り消しも使い切りも自然に実現できる。

トークンは `crypto.randomBytes(24)` の base64url（32文字）。

### 受験状況の考え方

| 状態 | 条件 | URLを開いたとき |
|---|---|---|
| 未受験 | 発行直後 | 面接を開始できる |
| 受験中 | 開始したが未完了 | **再開できる**（期限内） |
| 受験済み | 回答を送信済み | 「受付済みです」と表示。二度と開けない |
| 期限切れ | 期限を過ぎた | 担当者への連絡を案内 |
| 無効 | 人事が無効化 | 担当者への連絡を案内 |

**受験途中の離脱だけは、やり直せるようにしている。**
回線が切れた、ブラウザを閉じてしまった、という理由で
応募者が受験機会を失うのは避けたいため。
一方、完了後の再受験は認めない（選考の公平性のため）。

### 画面の文面について

期限切れや受験済みは、応募者側の落ち度ではない。
「URLが正しくありません」ではなく、状況ごとに文面を変えている。
受験済みなら「ご回答は受け付けております」、
期限切れなら「担当者へご連絡ください」。
選考を受ける側の体験は、その会社の印象そのものになる。

### 案内メール

外部のメール送信サービスは入れていない。代わりに、
**そのまま使える案内文をURL・期限つきで生成**し、コピーとメーラー起動を用意した。

理由は2つ。送信サービスを入れると送信ドメイン認証（SPF/DKIM）の設定が必要になり、
クライアント側の作業が増える。またこの環境では送信の検証ができない。
自動送信が必要になった時点で、Stage 3 以降に追加する。

### 積み残し

- 候補者の一括登録（CSV取り込み）… 応募数が増えたら
- 自動送信 … 上記の通り、必要になってから
- 候補者データの削除 … **Stage 4。実データを入れる前に必要**

## Stage 4 実装メモ

Stage 3（人事のログイン）より先に着手した。
Stage 2 で候補者URLを発行できるようになった時点で、
**次のデプロイから本物の応募者データが入りうる**状態になったため。
保護の仕組みが無いまま実データを受け入れることは避けたい。

### 入れたもの

| ファイル | 役割 |
|---|---|
| `db/003_privacy.sql` | 削除請求の受付表、自動削除のための索引 |
| `api/cleanup.js` | 保存期間切れの自動削除（Vercel Cron が毎日呼ぶ） |
| `api/privacy.js` | 保存方針の開示／削除請求の受付／完全削除 |
| `privacy.html` | 応募者向けの説明と削除請求フォーム |
| `interview.html` | 同意画面に、何が起きるかの具体的な開示を追加 |
| `dashboard.html` | 「この記録を完全に削除」（削除請求への対応） |

### 保存期間

環境変数で決める。クライアントの規程に合わせて変えるため。

| 変数 | 既定 | 対象 |
|---|---|---|
| `RETENTION_DAYS_SESSION` | 180日 | 面接記録（回答内容） |
| `RETENTION_DAYS_CANDIDATE` | 365日 | 候補者（氏名・連絡先） |
| `RETENTION_DAYS_AUDIT` | 730日 | 操作ログ |

`/api/cleanup` が毎日3時（日本時間）に走り、期間を過ぎたものを削除する。
**期間を決めただけでは守ったことにならない。** 実際に消える仕組みが動いていて
初めて「○ヶ月で消えます」と言える。

### 決めたこと

**論理削除にしない。**
「消してほしい」に対して「見えなくしました」は答えになっていない。
削除は行そのものを消す。

**削除請求は受け付けるが、削除は人が行う。**
フォームから届くのは「依頼」まで。本人確認をせずに削除まで自動化すると、
第三者が他人のデータを消せてしまう。

**依頼に含まれる個人情報も、対応後に消す。**
削除請求の記録には「いつ・どの依頼に対応したか」だけを残し、
氏名とメールアドレスは対応完了時に消去する。
削除の証跡が新たな個人情報の保管先になっては本末転倒。

**監査ログに回答内容を書かない。**
`data.purge` に残すのは件数だけ。人事メモも200文字で切っている。
ログは長く保持するので、そこに個人情報を流し込まない。

**開示文は、実際の設定を読んで表示する。**
「AIへ送信します」と書いてあるのに送っていない（またはその逆）を避けるため、
同意画面と説明ページは `/api/privacy` から保存期間とAI利用の有無を取得して文面を組み立てる。
デモとして開いた場合は「端末内にのみ保存」と表示される。

### クライアントと決める必要があるもの（こちらでは決められない）

- [ ] **保存期間の日数** — 上記は既定値。社内規程・就業規則との整合を確認いただく
- [ ] **既存の個人情報保護方針との突き合わせ** — 利用目的の記載、
      委託先（AIサービス）の明示が現行の方針でカバーされているか
- [ ] **問い合わせ窓口** — `PRIVACY_CONTACT` に設定する連絡先
- [ ] **保存先の暗号化設定** — データベース事業者側の設定（保存時の暗号化、
      バックアップの保持期間、リージョン）を確認のうえ確定する
- [ ] **AIサービスの利用条件** — 送信したデータの取り扱い（学習利用の有無、
      保持期間）を提供元の規約で確認し、必要なら契約を結ぶ

> ⚠️ ここに書いた文面は**技術的な雛形**であり、法務の確認を代替しない。
> 実運用の前に、クライアント側で内容を確認いただくこと。

### 積み残し

- **Stage 3（人事のログイン）が未着手** — いまは全員が同じ鍵。
  「誰が削除したか」まではまだ分からない
- 応募者本人による削除の即時実行（本人確認の仕組みが要る）

## Stage 3 実装メモ

### 入れたもの

| ファイル | 役割 |
|---|---|
| `db/004_users.sql` | 担当者テーブル、操作ログに担当者列を追加 |
| `api/_auth.js` | セッションCookieの発行と検証、権限判定 |
| `api/auth.js` | ログイン／ログアウト／初期設定 |
| `api/users.js` | 担当者の追加・権限変更・停止・キー再発行・操作ログ |
| `team.html` + `assets/js/team.js` | 担当者管理画面（管理者のみ） |

### 計画から変えた点：メールリンク認証 → 担当者ごとのアクセスキー

当初は「パスワードを持たない」メールリンク方式を想定していたが、
**メール送信の経路をまだ用意していない**（Stage 2 で意図的に見送った）。
送信サービスを入れると送信ドメイン認証の設定がクライアント側に発生し、
かつこの環境では配信の検証ができない。

代わりに、担当者ごとのアクセスキーを管理者が発行する方式にした。
Stage 3 の目的である
  ・誰の操作かが分かる
  ・個人単位で停止できる
は同じように満たせる。

ログインの入口は `api/_auth.js` に閉じてあるので、
メール送信を導入する段階で、このファイルだけ差し替えれば移行できる。

### 権限

| 権限 | できること |
|---|---|
| viewer（閲覧のみ） | 記録と候補者の閲覧 |
| reviewer（選考担当） | ＋ 合否とメモの記録、候補者の登録・招待 |
| admin（管理者） | ＋ 担当者の管理、データの完全削除 |

閲覧のみの担当者には、合否ボタンを押させない（画面上でも無効化）。
削除は取り消せないので admin に限定した。

### 決めたこと

**アクセスキーは平文で保存しない。** sha256 のハッシュだけを持つ。
発行時の1回だけ画面に表示し、以降は確認できない（忘れたら再発行）。
データベースが漏れても、そのまま鍵としては使えない。

**セッションはHttpOnly Cookieで持つ。**
画面のスクリプトからは読めないので、localStorage に鍵を置いていた
Stage 1 の方式より安全。有効期限は12時間。

**停止した担当者は、Cookieが残っていても即座に弾く。**
リクエストごとにデータベースで `disabled_at` を確認している。
署名の有効期限切れを待つ必要がない。

**自分自身を降格・停止できない。**
管理者が誰もいなくなる状態を作らないため。

**ログインの失敗理由を区別しない。**
「メールアドレスが違う」「キーが違う」を出し分けない（総当たりの手がかりになる）。

### 共有鍵（HR_ACCESS_TOKEN）の廃止

Stage 1 で入れた共有鍵は、**最初の管理者を登録するためだけ**の経路になった。

1. `HR_ACCESS_TOKEN` を設定した状態で `/team` を開く
2. 担当者が0人のあいだは初期設定として最初の管理者を作れる
3. 管理者を1人でも作ると、この経路は自動的に閉じる
4. **移行後は環境変数から `HR_ACCESS_TOKEN` を削除する**

### 積み残し

- 操作ログの画面は管理者のみ。担当者ごとの絞り込みは未実装
- Stage 1〜2 に記録された操作の `actor` は `'hr'` のまま
  （当時は誰か分からなかったため、遡って埋めることはできない）
- メールリンク認証への移行（メール送信を入れる段階で）
